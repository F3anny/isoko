How to use this document
This SRS is the single technical reference for design, implementation, testing, deployment and acceptance of Isoko. Every use case (Section 6) traces to shall-style requirements (Section 7), non-functional targets (Sections 9–12) and acceptance tests (Section 17, Appendix C). A tester who has never seen the code should be able to write a complete test plan from it; a Product Owner should be able to sign UAT against named behaviours instead of a demo.

1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) defines the complete functional and non-functional requirements of Isoko, a multi-vendor online marketplace built for East African buyers and small-business sellers. Isoko (Kinyarwanda for “market”) lets sellers list products, lets buyers pay with mobile money or card into escrow, and releases the seller’s money only when delivery is confirmed by a one-time code.
The platform is delivered as containerised services — web storefront, REST API and database at minimum — deployed through a CI/CD pipeline to Kubernetes, with monitoring and alerting built in. This document is the authoritative guide for design, development, verification, validation (UAT), operations and documentation.
1.2 Scope
In scope for Release 1 (MVP / capstone):
Guest browsing, search, filtering and product detail; wishlist for registered buyers.
Buyer registration, login, phone verification, session management and account lock-out.
Cart, discount codes (alphanumeric, 5–10 characters), quantity discount and free-shipping rules.
Checkout with MTN MoMo, Airtel Money or card; payment-timeout handling; escrow and OTP-confirmed delivery.
Multi-vendor seller onboarding (KYC), product listing, order fulfilment and payouts with commission.
Order lifecycle: Placed → Payment Pending → Paid → Shipped → Delivered → Completed, plus Cancelled, Payment Timed Out, Disputed and Refunded.
Admin console for moderation, refunds, dispute resolution and reporting; reviews and ratings.
English and Kinyarwanda UI (French and Swahili are Release 2), low-bandwidth PWA.
Containerisation (Docker), orchestration (Kubernetes/Helm), CI/CD (GitHub Actions + Argo CD), infrastructure as code, structured logging, dashboards, alerts and backup/restore.
Out of scope for Release 1 (see roadmap, Section 2.7):
Native Android/iOS apps (the PWA covers mobile in Release 1).
Internals of third-party payment gateways, mobile-money operators and courier systems — only the adapter contract and failure behaviour are in scope.
Isoko-operated warehouses (“fulfilment by Isoko”), buy-now-pay-later and cross-border trade.
ERP/accounting integration, and live production customer data during the academic project.

3.2 Development methodology
Agile delivery in four three-week sprints (Section 16) with a V-model discipline for quality: acceptance tests are designed while requirements are written, integration tests with module design, and unit tests with unit design. Each sprint ends with a verification checkpoint (pipeline green, coverage gate met, demo to Product Owner) and a short retrospective. Work is tracked as issues linked to requirement IDs.

4.5 Constraints
Currency is RWF; amounts are integers. Time zone is Africa/Kigali (CAT); timestamps stored in UTC.
Payment providers are accessed only through sandbox stubs in the academic environment; no real money and no real PII.
Hosting may be a local kind/minikube cluster or a cloud free tier; manifests must be portable (no vendor-specific APIs in application code).
All third-party components must use licences compatible with the project (open source preferred).
The design must keep Release 1 runnable on modest hardware (≤ 8 GB RAM for the full local stack).

UC-01 — Register account
Use case name
Register account
Summary / description
A guest creates an Isoko buyer account, verifies their phone and can then log in.
Actors
Guest (primary); SMS provider (supporting).
Trigger
“Create account” on the login page, or an anonymous user starts checkout.
Preconditions
The e-mail and phone number are not already registered.
Post-conditions / guarantee
On success a Customer exists with status=active and a verified phone. On failure no partial account is stored.
Main flow
1. System shows the form: name, e-mail, phone (07X…), password, confirm password.
2. Guest submits valid data.
3. System checks uniqueness, hashes the password (Argon2id) and creates the account as pending.
4. System sends a 6-digit OTP by SMS (valid 5 minutes).
5. Guest enters the OTP; system activates the account, signs the user in and sends a welcome message.
Extensions
2a. E-mail or phone already registered — show error, offer Log in.
2b. Password < 8 characters or lacking a letter and a digit — reject and re-prompt.
2c. Phone not a valid Rwandan mobile (10 digits, 07X) — reject (EP/BVA).
5a. OTP wrong — allow 3 attempts, then require a new OTP.
5b. OTP expired — offer “resend” (max 3 per hour).
Business rules
• E-mail and phone are each unique.
• Password policy: ≥ 8 characters, at least one letter and one digit.
• No account is activated until the OTP is verified.
Traceability
FR-AUTH-09..12 • UAT AU-011..AU-014

UC-02 — Log in
Use case name
Log in
Summary / description
A guest authenticates and becomes a Customer, Seller, Courier or Admin session. On failure access is denied and no session is created.
Actors
Guest (primary); auth-service, user store (supporting).
Trigger
Guest clicks “Log in”, or Checkout starts while unauthenticated («include» from UC-07).
Preconditions
The login page is reachable. An account may or may not exist.
Post-conditions / guarantee
On success the user is signed in and returned to the previous page. On failure access is denied, the failed-attempt counter is updated, and the password is never echoed or logged.
Main flow
1. System prompts for e-mail (or phone) and password, or to register.
2. User submits credentials.
3. System validates them against the user store (sequence: Figure 14.1).
4. System issues a session (Secure, HttpOnly cookie), merges any anonymous cart and restores the previous page.
Extensions
1a. No account — «extend» Register (UC-01), then continue at step 4.
3a. Invalid credentials — «extend» Display error message: generic “email or password is incorrect”; increment attempts; back to step 1.
3b. Third consecutive failure — lock account 30 minutes, send security notification, write audit record.
3c. Account locked or disabled — same generic error; never confirm the account exists.
3d. Seller/Admin role — require a second factor (TOTP or SMS OTP) before issuing the session.
*a. User cancels — no session. *b. Connection lost — no session created.
Business rules
• Passwords stored hashed (Argon2id); never logged (only inputLen).
• Cookies: Secure, HttpOnly, SameSite=Lax; idle timeout 30 minutes.
• Lock-out after 3 failures for 30 minutes; login p95 ≤ 500 ms at 100 concurrent users (NFR-PERF-03).
Traceability
FR-AUTH-01..08, 13, 14 • UAT AU-001..AU-010 • Figure 14.1

UC-05 — Manage cart
Use case name
Manage cart
Summary / description
The user adds, changes and removes items in a cart (anonymous or authenticated).
Actors
Guest or Customer.
Trigger
“Add to cart” or opening the cart.
Preconditions
Product is published and in stock for the requested quantity.
Post-conditions / guarantee
On success the cart reflects the change and totals recalculate. On failure the cart is unchanged.
Main flow
1. User selects quantity ≥ 1 and adds the item.
2. System checks stock and shop status.
3. System adds or increments the line and recalculates subtotal.
4. User may change quantity or remove lines; cart persists for the session and across login.
Extensions
2a. Quantity > stock — reject and show remaining quantity.
2b. Product became unpublished — reject.
4a. Anonymous cart merged on login — quantities add, capped by stock, no duplicate lines.
Business rules
• Stock is not reserved until checkout begins (reservation TTL 10 minutes).
• Cart holds items from multiple shops; order is split per shop at checkout.

UC-06 — Apply discount
Use case name
Apply discount
Summary / description
The customer applies a promotional code to the cart. Invalid codes never reduce the price.
Actors
Customer.
Trigger
Customer enters a code and selects Apply.
Preconditions
Cart has at least one line; customer is logged in at checkout.
Post-conditions / guarantee
On success totals show the discount. On failure totals are unchanged and a field-level error is shown.
Main flow
1. Customer enters a code.
2. System validates length, character set, existence and validity window.
3. System applies the rule (percentage, fixed amount, or free shipping) and redraws totals.
Extensions
2a. Length 1–4 or 11+ — “code must be 5–10 characters”.
2b. Non-alphanumeric (e.g. SAVE-25!) — “code contains invalid characters”.
2c. Unknown, expired or used-up code — “code is not valid”.
2d. Minimum quantity/value not met — explain the rule; totals unchanged.
Business rules
• Codes are alphanumeric, length 5–10 (EP + BVA, Appendix A).
• Automatic quantity discount: 10 % when ≥ 5 items; not stacked with a code — the larger discount wins.
• At most one code per order; a discount never takes a line below 0 RWF and never exceeds 50 % of subtotal.
Traceability
FR-DISC-01..08 • UAT DISC-001..DISC-010 • Appendix A

UC-07 — Checkout / place order
Use case name
Checkout / place order
Summary / description
The customer converts the cart into an order and receives an order number.
Actors
Customer (primary); Payment Gateway, Notification service (supporting).
Trigger
Customer selects “Checkout”.
Preconditions
Non-empty cart; items still in stock.
Post-conditions / guarantee
On success an Order exists in Placed (then Paid if payment succeeds) and the customer receives an order number. On failure no order is left in a charged state, the customer is not charged, and stock reservations are released.
Main flow
1. «Include» Log in if the session is anonymous.
2. System shows order summary per shop; customer confirms address or selects a pickup point.
3. Optional: «extend» Apply discount (UC-06).
4. System displays the invoice: subtotal, shipping, discount, total (RWF).
5. Customer chooses MoMo, Airtel Money or card and confirms.
6. System creates the order (Placed), reserves stock and «include» Pay order (UC-08).
7. System shows “transaction successful” with the order number and sends notifications.
Extensions
1a. Log in fails — cancel reservation; customer not charged.
2a. Customer edits address — back to step 2.
5a. Customer changes payment method — back to step 4.
6a. Payment declined or timed out — see UC-08; order not Paid.
6b. Double submit — idempotency key returns the same order; no second charge.
*a. Customer cancels — confirm dialog, release reservation. *b. Connection lost — reservation expires; no charge. *c. No payment confirmation within 10 minutes — cancel, “return to cart and try again”.
Business rules
• Free shipping when subtotal ≥ 50,000 RWF or buyer tier = Gold (Appendix A).
• Card numbers are never stored; only a gateway token/reference.
• Place-order is idempotent (Idempotency-Key).
• Orders are split per shop so each seller fulfils and is paid separately.

UC-08 — Pay order (escrow)
Use case name
Pay order (escrow)
Summary / description
The platform requests a charge from the payment adapter and records success, failure or timeout; successful payments are held in escrow.
Actors
Customer; Payment Gateway.
Trigger
Included from Checkout step 6, or “Retry payment” on a Placed / PaymentTimedOut order.
Preconditions
Order is Placed (or PaymentTimedOut for retry); amount > 0.
Post-conditions / guarantee
On success Order=Paid, payment=held, stock committed. On failure or timeout Order is not Paid and the customer is not charged.
Main flow
1. System sends charge(amount, method, orderId, idempotencyKey) to the adapter; order=PaymentPending.
2. Customer approves on their phone (PIN prompt) or completes 3-D Secure.
3. Gateway calls back with success and reference; system verifies the HMAC signature.
4. System sets payment=held, order=Paid, writes audit, publishes PaymentCaptured, notifies buyer and seller.
Extensions
3a. Gateway declines — order returns to Placed; show reason; allow retry.
3b. No callback within 45 s — worker polls status; if still unknown, order=PaymentTimedOut; never assume Paid; stock released after 10 minutes.
3c. Duplicate or replayed callback — ignored if already processed (idempotent).
3d. Late callback after timeout — reconcile: mark Paid if funds captured, otherwise auto-refund.
Business rules
• Unknown outcome is never treated as success.
• Adapter internals are out of scope; contract is in Section 8.4.
• All money movements are written to an append-only ledger.
Traceability
FR-PAY-01..12 • UAT PAY-001..PAY-014 • Figure 14.2
