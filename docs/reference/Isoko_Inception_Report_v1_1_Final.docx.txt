1. Executive summary
This Inception Report is submitted as Milestone 1 of the SPEDO501 integrated capstone. It marks the formal start of work on Isoko, a mobile-money-first, multi-vendor marketplace for East Africa: a web storefront/PWA, REST API and database services, seller and admin workflows, escrow payments, and delivery confirmation. The platform is delivered through containerisation, CI/CD and Kubernetes, with monitoring and alerting built in.
The product scope is defined in the Software Requirements Specification ISK-SRS-2026-001 v1.0, including use cases, functional requirements, non-functional requirements, security requirements and acceptance traceability. The companion UAT pack is ISK-UAT-2026-001. This Inception Report binds those requirements to the project plan, milestones, risks, resources, communication approach and working assumptions.
Reading instruction for testers: the report’s objectives, out-of-scope list and technical approach must remain consistent with the SRS and UAT materials. Release 1 is a PWA-based marketplace; native Android/iOS applications, live payment gateway internals, Isoko-operated warehouses, buy-now-pay-later, cross-border trade and live production customer data remain outside the academic scope.
2. Project background and programme context
SPEDO501 Perform DevOps requires trainees to configure an environment, execute tests, monitor logs and prepare documentation against one running scenario. Isoko is the selected scenario: a green-field, mobile-first marketplace where buyers can browse and purchase from multiple sellers, pay through MTN MoMo, Airtel Money or card, and have successful payments held in escrow until delivery is confirmed. The platform is designed as containerised services with Kubernetes, CI/CD, structured observability and security controls.

6. Technical architecture overview
Detail lives in the Isoko SRS Sections 8–12. The inception-level architecture uses a mobile-first PWA storefront, REST services, PostgreSQL, Redis, RabbitMQ, payment and notification adapters, Docker containers and Kubernetes. CI/CD uses GitHub Actions and Argo CD, with structured logging, Prometheus/Loki/Grafana observability and alerting. UAT and load/security testing are performed in the Kubernetes staging environment using synthetic data.

11. Quality and UAT approach
UAT objectives derived from the Isoko SRS acceptance scenarios:
A buyer can register, verify a phone number, browse products, manage a cart and complete a successful checkout using a supported payment method.
A seller can complete the required onboarding/listing and fulfilment workflow, subject to the specified KYC and approval rules.
A payment timeout or other uncertain payment outcome does not incorrectly mark an order as Paid, and money/stock consistency is preserved.
A seller/courier workflow can move a paid order through shipping and delivery confirmation using the required delivery OTP.
UAT records task success and the defined usability/acceptance evidence, while performance, reliability and security targets are verified through the appropriate test activities.
Entry criteria: staging environment available; SRS baseline; UAT/test materials; synthetic seed data; smoke tests green. Exit criteria: required acceptance cases pass or are formally waived; no open Critical defects; Product Owner acceptance is recorded.
